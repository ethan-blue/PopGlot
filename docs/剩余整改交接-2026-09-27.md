# PopGlot 剩余整改交接（2026-09-27）

供接手 AI 执行。先阅读 `GROK-CLI-整改任务书-2026-09-26.md`、`整改结果-2026-09-26.md` 和 `product-review-2026-09-26/UI-RECHECK-2026-09-27.md`。本文件汇总剩余范围并补充用户最新的译文排版要求。先核实当前实现，不将旧清单全部当成未修复；保留已有未提交改动。

## 1. 译文段落与自动排版（P1，用户明确反馈）

现象：原文已有换行、段落，翻译后却变成一大段，阅读费力。用户需要默认得到易读的译文，不要每次手动整理。

### 产品规则

- 默认保留原文有意义的结构：标题、自然段、独立短行、对话、列表、步骤、引用、签名等。不同段落不能无故合并。
- 多段文本按语义分段，段落间保留清晰间距；列表一项一行，对话按说话人分行。不能为了美观强行把所有文字变成列表，也不能机械地每句话换一行。
- 对 OCR/PDF 的错误断行，可在同一段内合并被截断的句子，再按可辨认的语义恢复段落。分不清是否为错误断行时优先保留，不擅自吞并结构。
- 原文确实是长段落时，可以在自然语义转折处分段，但不能增加标题、论点、解释、总结或省略内容；语义与顺序必须保持。
- 短词、单句保持简洁，不额外输出“以下是翻译”“整理后的内容”等前言。
- 翻译与总结分开。翻译排版不能变成内容改写或摘要，不得静默发起第二次请求或增加计费。
- 代码、命令、路径、URL、数字、单位、占位符、表格关系不得因排版改变；代码块内部空白遵循既有逐字保真要求。
- 自定义提示词仍受内容保真及固定输出协议约束，不能借此改变网络地址、权限或自动收集范围。

### 必须先定位实际丢失位置

用不含隐私的固定样例，逐层对照：输入原文 → 请求提示词 → 模型原始响应 → 协议解析后的译文 → 存储文本 → 流式/最终渲染 → 复制/导出。

重点检查 `crates/popglot-domain/src/prompt.rs`、`crates/popglot-core/src/provider.rs`、`Services/MarkdownPresenter.cs`、TranslationCoordinator、ReadingModeState，以及工作台、浮窗、快速查词、资料库。检查是否有全局空白折叠、换行替换、普通 Markdown 软换行折叠、流式切换最终渲染导致的结构丢失。根因未确定前，不把问题全部归咎于模型。

### 建议加入翻译提示词的约束

> 保留原文的标题、段落、列表和有意义的换行，不要把多段内容合并为一段。对于明显由 OCR 或页面宽度造成的断行，只在同一语义段落内合并；必要时按语义整理自然段，使译文清晰易读。不要新增原文没有的内容，不要总结或省略，不要输出排版说明。代码、命令、链接、数字及占位符保持原样。

此段是翻译内容规则，需嵌入已有提示词结构，不得覆盖或破坏固定 JSON/其他输出协议。若模型响应已包含正确换行，应修复显示/解析链路，而非再请求一次排版。

### 显示与数据约束

- 区分源文本、译文内容与显示格式；不覆写原文或批量重写已有历史记录。
- 自动排版后的译文应在工作台、浮窗、资料库中保持相同语义结构。复制与导出要保留段落、列表及必要换行，不能只在屏幕上有间距。
- Markdown 的软换行、硬换行、空行分段要有明确策略，不能用通用正则把全部换行删除；不要通过全局替换换行破坏代码和表格。
- 流式完成切到最终视图时，段落不得突然合并，用户向上阅读时不得强制拉回底部。

### 必须补充的验收样例

| 样例 | 预期 |
| --- | --- |
| 三段邮件，末尾有署名 | 三段正文与署名独立，不粘连 |
| 单换行分隔的对话、地址或诗行 | 有意义的独立行保留 |
| 标题、正文、三条编号步骤 | 层级保留，步骤一项一行 |
| OCR 将一句话切成三行，两段间有空行 | 合并段内断句，但保留两段 |
| 无空行的连续长文 | 仅在合理语义边界分段，内容无增删 |
| 中文、英文及混合代码围栏 | 段落清晰，代码字节与缩进不变 |
| Markdown 表格、嵌套列表、链接 | 结构及链接目标不变 |
| 单词、短语、单句 | 不额外分段，不产生前言或总结 |
| 相同译文经过流式、终态、历史、复制和导出 | 各阶段结构一致 |

先用固定模型响应替身验证解析/显示链路，再在获得授权后验证真实模型质量。分别记录“结构保真”和“翻译质量”，不能把提示词字符串测试当作真实翻译通过。

## 2. UI 与产品体验

- 逐页检查工作台、引擎列表/编辑、表达方式、通用设置、资料库、浮窗、快速查词、帮助窗口。
- 统一字号、输入框/按钮/下拉框尺寸、圆角和间距；保留表单与紧凑工具栏的合理差异，避免裁切与巨大的空白。
- 深浅色统一背景层级、控件边框、强调色和状态色；减少套框，保留焦点与对比度。
- 检查窄窗标题/工具栏重叠、搜索框压字、帮助边框重叠、中文 IME 与不同 DPI。
- 精简常驻说明和技术术语，管理入口只写“管理”。不删除必要的错误原因、隐私和额外请求提示。
- 定位文字隐藏/收起切换时文字过多的具体入口；统一图标、悬停提示与读屏名称。
- 已有输入框内边距及文案修复要回归验证，不要直接覆盖回旧实现。

## 3. 引擎配置

- 验证模型列表长列表滚动、靠近屏幕边缘、空列表、手动输入和中文输入。
- Key 未填写、已保存、替换中、已清除四种状态清晰；验证清除、保存、取消、重新打开的实际存储结果。
- 回归列表和编辑器测试的异步竞争：修改、切换、删除、重复点击时不得用旧结果覆盖新配置。
- 目录读取与生成测试分开；文字、流式、图片能力分别验收，不能用“获取模型成功”推断全部可用。

## 4. 阅读、总结及内容质量

- 检查译文/要点切换、缓存隔离、取消、失败与重新翻译，防止旧结果串入。
- 验证 Markdown 表格、嵌套列表、链接、未闭合围栏、长文性能和滚动。
- 使用短语、对话、邮件、技术文档、代码混排、表格及 OCR 样例检查译文是否准确、自然、无冗余；总结另行验证，不混入翻译。

## 5. SDK、可靠性与交付

- SDK 当前主要接管请求构造，核查固定版本、vendor 补丁、许可证和校验；保留有界读取、取消及流式约束，不宣称全面迁移。
- 回归导出防覆盖、删除/清空撤销、写入失败恢复、资料库窄窗。
- 验证 Tab、Enter/Esc、读屏、中文 IME、100/125/150/200% DPI 及高对比度。
- 明确实际运行 exe 与新构建目录，不将旧程序截图作为新版本验收。

先复现和定位，再修改与回归。每项标注“通过 / 不通过 / 未验证”，附代码位置、命令和证据。UI 需深浅主题截图及实际交互验证；构建成功不等于视觉合格。
