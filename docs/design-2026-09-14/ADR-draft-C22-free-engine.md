## 一、背景与现状事实

### 1. 现有技术资产与约束
- **核心实现**：`apps/PopGlot.Windows/Services/FreeTranslateService.cs` 与 `crates/popglot-core/src/provider.rs`。
- **授权防御网（已闭环通过验证）**：
  - **C01 授权令牌**：`OutboundPolicy.TryClaimSend` 采用硬件级原子操作（`Interlocked.Exchange`），保证任何竞态下真实出网严格单次扣除；
  - **用户意图状态机**：`ShellSettings.FreeEngineConsent` 具备 `Unset`（未决）、`Allowed`（已同意）、`Denied`（已拒绝）三态；
  - **空态自愈引导**：无自备 API Key 且未同意免费引擎时，工作台呈现错误自愈引导卡，绝不静默出网；
  - **离线与断网测试**：PureTests 与 LogicTests 均包含“0 次非授权公网发送”严格断言。
- **现存商业与法律问题**：
  - 目前的内置免费引擎调用的是由开发团队搭建或托管的公共代理端点，目前无正式的服务条款（ToS）、服务等级协议（SLA）与商用防刷计费机制；
  - 软件若公开分发，集中式公共端点将面临无法预测的流量爆发、第三方滥用（爬虫/脚本）、IP 被封禁以及云端账单失控风险；
  - 若定位为纯生产力工具，团队是否愿意持续承担公共云端代理的运营与合规成本，决定了产品的技术架构走向。

## 二、三个可选方案与取舍矩阵

```
  方案 A (双轨并行)              方案 B (纯 BYOK)             方案 C (可选扩展插件)
 ┌──────────────────────┐      ┌──────────────────────┐      ┌──────────────────────┐
 │ 自带Key + 内置免费通道 │      │ 纯客户端/零托管服务   │      │ 默认纯净，按需启用    │
 │ (开箱即用，团队承担运维)│      │ (自备Key/本地模型直连)│      │ (免费通道作为可插拔项)│
 └──────────────────────┘      └──────────────────────┘      └──────────────────────┘
```

### 方案 A：保留内置免费引擎（双轨并行模式，现状优化）

#### 1. 方案说明
维持当前“全新安装带内置免费通道 + 支持自备 API Key（BYOK）”双轨模式。
在当前代码基础上：
1. 为免费引擎增加每日请求上限配额（如每台设备 100 次/天，由本地与端点协同计数）；
2. 首次使用时弹出正式的服务条款与隐私摘要确认框；
3. 保留并加固 `FreeTranslateService` 与 `OutboundPolicy`。

#### 2. 多维取舍评估
- **商业影响**：
  - *优势*：初次安装转化率最高，普通用户“下载即可用”，有利于早期快速扩散与口碑建立；
  - *劣势*：运营方持续产生服务器与大模型 Token 成本；若无商业化变现（如付费订阅），属于纯负现金流投入；存在被逆向提取 API 的合规风险。
- **技术成本**：低。当前 C01 授权网关已完全闭环且测试全绿，代码已在生产路径就绪，仅需补充轻量配额限制。
- **隐私叙事**：良好但需解释。“PopGlot 提供开箱即用公共通道，数据经由官方加密代理中转（零日志保存）；若需极致隐私，建议配置个人 API Key 或纯本地模型”。
- **用户迁移影响**：零冲击，现有测试版本与早期用户完全无感。
- **商业门禁（README §5）兼容性**：需要补齐运营端点的商用服务条款与隐私政策 URL。

---

### 方案 B：首个商业版彻底移除免费引擎（纯 BYOK / 本地模式）

#### 1. 方案说明
彻底下线并剥离 `FreeTranslateService` 及公共端点。应用重新定位为**“绝对中立的开源/独立桌面客户端”**。
1. 出厂仅包含 Provider 预设目录模板（DeepSeek、OpenAI、Anthropic、Gemini、Ollama 本地大模型等）；
2. 首次启动时引导用户“填入第一个 API Key”或“选择本地 Ollama 引擎”；
3. 工作台空态卡片明确提示“请先配置翻译引擎”。

#### 2. 多维取舍评估
- **商业影响**：
  - *优势*：**运营团队零成本、零账单、零连带法律风险**。彻底摆脱“软件免费但作者在替用户交 API 账单”的陷阱；合规性最强，可直接进入企业采购与应用商店（Microsoft Store）上架；
  - *劣势*：初次体验门槛高。无 API Key 或不懂 AI 服务的用户可能因“无法开箱即翻”而直接卸载。
- **技术成本**：极低且实现代码净减。下线 `FreeTranslateService`、精简 `OutboundPolicy`，彻底消除免费引擎双发/授权竞态相关的维护负担。
- **隐私叙事**：**极致强劲**。“PopGlot 是完全属于您的本地工具，我们没有自己的服务器，绝不触碰、中转或记录您的任何字符。数据从您的电脑直达您信任的服务商，或在您的显卡上纯离线运行”。
- **用户迁移影响**：中等。已配置 API Key 的用户无影响；仅依赖免费引擎的用户在升级后会被引导至设置页添加自备服务商。
- **商业门禁（README §5）兼容性**：天生完美契合商业门禁，无需任何运营云端基础设施。

---

### 方案 C：免费引擎降级为默认关闭的可选扩展（按需知情激活）

#### 1. 方案说明
折中路线：**核心程序默认为纯 BYOK 架构，但内置一个“实验性公共翻译通道”插件开关**。
1. 全新安装时不激活免费引擎，状态为禁用（`Disabled`）；
2. 用户在设置窗体中可主动开启“启用社区公共翻译网络”；
3. 开启时展示知情同意卡片，说明这是由社区或赞助者提供的免费算力，存在每日限额、不可用于商业敏感内容；
4. 发生拥堵或限流时自动降级并推荐自备 Key。

#### 2. 多维取舍评估
- **商业影响**：兼顾开箱体验与团队风险控制。只有确实无自备 Key 的长尾用户才会主动开启，大幅降低集中并发请求量；同时为未来推出“PopGlot Pro 官方高速订阅”预留了无缝切入的架构槽位。
- **技术成本**：中等。需在 `SettingsWindow` 与 `ServicesSection` 中重塑开关逻辑，状态机由现在的“弹窗询问”迁移为“设置项主动拨动”。
- **隐私叙事**：优秀。“默认零出网、纯客户端；用户明确知情授权后方可按需连接公共免费算力”。
- **用户迁移影响**：平滑。现有同意过免费引擎的用户可无感继承。
- **商业门禁（README §5）兼容性**：合规性优良，可满足各应用市场对第三方增值服务透明度的要求。

## 三、三方案综合对比矩阵

| 维度 | 方案 A：双轨并行（现状） | 方案 B：纯 BYOK（移除免费） | 方案 C：可选扩展（默认关闭） |
|---|---|---|---|
| **首发获客门槛** | 极低（点开即翻） | 较高（需自备 Key/本地模型） | 中（可一键开启） |
| **运营资金成本** | 持续产生 API / 服务器费用 | **绝对零成本** | 可控（低频长尾流量） |
| **法律与合规风险** | 需持续防范爬虫与恶意滥用 | **零风险（纯客户端中立）** | 极低（明确责任与免责） |
| **隐私宣传力度** | 需解释中转代理机制 | **极致隐私（无服务器）** | 优秀（默认本地，知情连接） |
| **代码变动与维护** | 保持现状（需加频控） | 净减代码（彻底删除代理服务） | 需调整开关交互 |
| **未来商业化演进** | 易产生“一直免费”的用户惯性 | 易演进为专业付费软件（买断） | **极佳（公共通道可转为订阅）** |

## 四、工程准备就绪声明（无论选择何种方案）

1. 若选择 **方案 A**：当前 `FreeTranslateService.cs` 与 `OutboundPolicy.cs` 代码与测试（C01 授权）完备，可直接打上版本号进入验收；
2. 若选择 **方案 B**：开发团队可在 1 个轻量波次内完全剥离免费端点，将空态完全对齐为“添加您的第一个 Provider”；
3. 若选择 **方案 C**：开发团队可在设置服务页增加“公共体验通道”卡片与 Consent 状态机。
