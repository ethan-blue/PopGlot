# 第一部分：【主题体系】规划承诺 vs 现实

## 1.1 用户最关心的 4 个核心疑问澄清

用户在日常使用或讨论中，常会隐约记得某些关于“个性化”、“换肤”、“主题”的规划。此处先给出正面定性：

1. **“能不能自己建主题、自定义调色盘（自定义主题）？”**  
   - **结论：规划文档从未承诺过此功能（NOT_PLANNED）**。  
   - **文档事实**：总纲 `REFACTOR_MASTER_PLAN.md:5` 开篇即明确“*范围：先修产品契约和基础架构，再重做交互与视觉；不以‘换一套配色’冒充重构*”；`DESIGN_SYSTEM.md` 锁死了中性表面与克制蓝紫。设计理念始终坚持“极简、低视觉噪音、工具属性”，从未把 PopGlot 定位为支持第三方主题或自由换肤的玩具。用户记忆中的“自定义”通常是把“自定义翻译引擎（Custom Provider）”或“自定义 Prompt”移情到了主题上。
2. **“能不能自己挑强调色（如红色、绿色、橙色等强调色选择）？”**  
   - **结论：规划文档明确禁止多强调色，从未规划用户选择（NOT_PLANNED）**。  
   - **文档事实**：`REFACTOR_MASTER_PLAN.md:263` 规定“*只使用一个强调色。成功、警告、失败同时提供图标和文本，不仅靠颜色*”；`UX_DECISIONS.md:10` 规定“*强调色只用于状态与主操作*”。历史上出现过的不同颜色，是产品内部版本演进（v0.1.0 亮蓝 → v0.1.1 azure 蓝 `#1A63D8/#4D9FFF` → v0.1.3+ 锁定为低饱和蓝紫 Light `#5563B8` / Dark `#7C89D9`），并非开放给用户的选择器。
3. **“主题选择（跟随系统 / 深色 / 浅色）现在能不能用？”**  
   - **结论：能用，已经完整实现（DONE）**。  
   - **代码事实**：设置页「通用设置」有主题下拉框，支持“系统默认 (跟随系统)”、“浅色模式”、“深色模式”三档，持久化保存在 `ShellSettings.Theme` 中。
4. **“改主题时的‘即时预览与退出还原’做到了吗？”**  
   - **结论：部分实现但有缺陷（PARTIAL）**。  
   - **代码事实**：下拉框一切换就会立即在内存中应用新主题（即时预览），但退出设置时并未提供干净的“自动还原”逻辑；若用户放弃保存，必须在底栏显式点“放弃修改”才会恢复，且提示文案未声明生效时机差异。

## 2.3 底层已有资产说明：PopGlot 的 Prompt 底座其实非常健康

虽然用户层功能为 0，但这**并不意味着产品在原地踏步**。需要向用户如实说明：
PopGlot 在 `crates/popglot-core` 层面建立的 **Prompt 协议安全红线是目前整个项目中最稳固的部分**（由 `crates/popglot-core/tests/prompt_contract.rs` 中 14 项机器测试死死守住）：
1. **源文绝对隔离**：用户输入的待翻译文本绝不拼接进 System Prompt，必须独立放在数据层（防止 Prompt 注入攻击）；
2. **Delimiter 随机隔离**：每次翻译使用随机生成的隔离标记，黑客无法靠伪造 XML/Markdown 标签逃逸；
3. **代码与 Token 绝对保护**：代码块、路径、变量占位符强制高于任何自然语言指示；
4. **流式保真度硬门**：模型中途若吐出无关废话或格式损坏，底层校验器会自动截断拦截。

**简言之：地基（安全防线）已经打得无比扎实，但地上的房子（用户界面与编辑功能）尚未动工。**

## 2.4 Prompt 侧「最小实现路径」建议（若要兑现，第一步做什么）
