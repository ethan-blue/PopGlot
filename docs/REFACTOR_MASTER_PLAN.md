# PopGlot 产品、UI 与架构重构总纲

> 版本：2026-08-27 审查稿  
> 用途：作为产品、设计、WPF、Rust、测试 Agent 的统一执行基线  
> 范围：先修产品契约和基础架构，再重做交互与视觉；不以“换一套配色”冒充重构

## Executive Summary

- **当前最大问题不是美术，而是产品结构。** 主窗口同时承担翻译工作台、设置中心、供应商编辑器、截图策略、生词本和历史记录，导致高频任务与低频配置混在一处。视觉上的“AI 味”只是这种信息架构失焦的外显。
- **必须先封住正确性与隐私问题。** 极速查词在安全离线模式下仍可能调用免费在线翻译；默认“打开主窗口”快捷键没有处理分支；测试连接会先保存草稿；全局取消句柄会在并发请求下取消错对象。这些问题不解决，重做 UI 只会让错误更漂亮。
- **产品定位应收窄并变得可感知。** PopGlot 不应追求复制一个功能大全，而应成为“面向技术阅读的快速、透明、可校验翻译工具”：选词、截图和输入只是三个入口，最终都进入同一个翻译会话；用户始终能知道内容是否出网、用了哪个引擎、代码 Token 是否完整。
- **Pot 只借鉴工作流模块化，不照抄外观和功能体量。** 借鉴其把选词、输入、剪贴板、截图、OCR、翻译服务和插件拆成独立能力的方式；不要在基础体验未稳定前追逐多服务并排、插件市场、划词悬浮球等广度。

## 1. 已验证的现状

### 1.1 技术与仓库

- Windows 客户端：WPF / .NET，托盘常驻，包含主窗口、翻译浮窗、截图遮罩、极速查词和悬浮触发器。
- 核心：Rust workspace，`popglot-domain` 负责路由与 Token 保护，`popglot-core` 负责配置和 Provider，`popglot-ffi` 通过 JSON + C ABI 暴露给 WPF。
- 当前自动验证通过：Rust 测试、Clippy、WPF 构建和逻辑测试均为绿色。绿色测试只能证明现有单元级契约未破坏，不能证明跨窗口隐私、并发取消和完整用户旅程正确。
- 当前工作树存在大量未提交修改。重构必须在独立 worktree/分支中进行，禁止以覆盖、reset 或格式化全仓库的方式“清理”。

### 1.2 产品表面

现有主窗口的六组导航同时混入：翻译、快捷键与外观、供应商、截图/OCR、生词本/Anki、历史记录。它把“每天用几十次的任务”和“偶尔修改一次的系统配置”放在同一层级，还用一个全局底部保存条承接不同页面的修改。

现有供应商页把厂商预设、协议、文本模型、视觉模型、API Key、联网、安全模式、解释、Token 保护、Base URL、Endpoint、自定义 Header 和 TLS 全铺在一页。用户被迫理解内部实现模型，且无法清楚回答三个基本问题：

1. 现在文字翻译到底用哪个服务？
2. 截图会不会上传，上传给谁？
3. 这个“测试连接”会不会改动我当前配置？

### 1.3 已确认的 P0 风险

| 编号 | 问题 | 证据 | 用户影响 |
|---|---|---|---|
| P0-01 | 极速查词绕过安全离线策略 | `QuickSearchWindow.xaml.cs` 在安全模式或未配置 Key 时直接落到 `FreeTranslateService` | 用户明确要求离线，文本仍可能出网 |
| P0-02 | 默认“打开主窗口”快捷键无处理分支 | `ShellSettings` 注册 `ShowWindow`，`App.HandleHotkey` 的 default 抛异常 | 默认快捷键可触发未处理异常 |
| P0-03 | 保存设置时丢失“打开主窗口”快捷键 | `MainWindow.Save_Click` 创建 `ShellSettings` 时未传该字段 | 保存其他设置后快捷键静默回退或丢失 |
| P0-04 | 测试连接会持久化草稿 | `TestConnection_Click` 先调用 `SaveProviderSettings()` | “测试”产生隐藏副作用，错误草稿污染正式配置 |
| P0-05 | 免费在线引擎缺少明确同意边界 | 缺少 Key 时主链路会回退 Google 公共翻译端点 | 首次使用的出网行为与用户预期不一致 |
| P0-06 | 安全策略由多个窗口重复解释 | `CoreBridge`、`QuickSearchWindow`、设置页各自判断网络/安全/凭据 | 同一设置在不同入口产生不同结果 |
| P0-07 | FFI 只有一个全局活动取消槽 | `ACTIVE_REQUEST` 保存最新请求，C# 任意 token 取消都调用全局取消 | A 请求取消可能误伤更新的 B 请求 |
| P0-08 | 自动截图路由并未使用真实内容信号 | 路由前将代码、复杂布局、质量、OCR 置信度填成固定默认值 | “智能自动路由”的解释强于实际能力 |
| P0-09 | 供应商共用一个旧式 Credential Target | `PopGlot/OpenAICompatibleApiKey` | 切换厂商会覆盖同一份 Key，无法形成多配置 |
| P0-10 | 浮窗“展开到主窗口”链路未接通 | 创建翻译面板时展开回调为 `null` | 控件可见但关键动作无完整结果 |
| P0-11 | 生词“导出 CSV”实际导出 Markdown | XAML 文案与 `ExportToMarkdown()`/`.md` 实现不一致 | 功能名、格式和文件结果冲突 |
| P0-12 | 配置写入非原子且损坏时静默回默认 | Rust 设置使用直接 `fs::write`，反序列化失败缺少可恢复反馈 | 进程中断可损坏配置，用户不知道为何被重置 |
| P0-13 | 旧配置迁移可能自动放宽联网权限 | 迁移文档称缺少 `network_enabled` 时应为 false，`serde(default)` 的实际默认却为 true，且图片上传默认开启 | 升级后可能在未重新同意的情况下允许文本/图片出网 |
| P0-14 | Rust Core 锁跨越网络请求 | FFI 持有 Core 读锁执行完整网络往返，保存设置需写锁且由 UI 同步触发 | 翻译中保存或切换语言可能冻结 UI 直到超时 |

## 2. 产品重新定位

### 2.1 一句话定位

**PopGlot 是面向技术阅读场景的 Windows 快速翻译工具：少打断、可校验、出网透明。**

### 2.2 核心用户承诺

1. **快：** 从快捷键到出现可交互结果壳，不让用户等待完整模型响应。
2. **准：** 标识符、路径、命令参数和异常名可校验；不能确认时明确失败或降级，不能伪装成功。
3. **透明：** 每次请求都能说明使用了本地 OCR、免费在线服务或用户配置的 Provider；截图上传必须有明确权限。
4. **少打扰：** 高频翻译无需打开设置中心，失败可在原位修复或跳转到对应配置。
5. **可恢复：** 设置、历史和生词写入可恢复；取消、重试和切换入口不污染其他会话。

### 2.3 暂不追求

- 不在第一阶段复制 Pot 的全部插件、剪贴板监听、多服务并排结果和外部 HTTP API。
- 不在基础状态模型未统一前增加更多浮窗形态。
- 不用大模型自动生成大量营销文案、图标、卡片和动画来掩盖流程问题。
- 不以“支持很多模型名”作为供应商体验完成的标准。

## 3. 目标信息架构

将产品拆成三个表面，所有入口共享一个翻译会话与同一套策略。

```text
选中文本 ─┐
截图区域 ─┼─> TranslationCoordinator ─> TranslationSession ─> 结果浮窗
手动输入 ─┘             │                       │
                        ├─ 出网/上传策略          ├─ 历史、生词
                        ├─ OCR/Provider 选择      └─ 诊断与耗时
                        └─ Token 完整性

控制中心：通用设置 / 服务 / OCR 与隐私 / 数据 / 高级
资料库：历史 / 生词，可由结果浮窗或控制中心进入
```

### 3.1 工作表面：统一快速翻译

- “极速查词”和主窗口的文本翻译合并为一个轻量输入表面。
- 默认按 Enter 提交，输入时自动联网翻译改为显式可选；不得把每次键入都默认发送到云端。
- 选词、截图、输入共享语言对、请求状态、取消、错误、历史和 Provider 诊断。
- 首屏只保留：输入/原文、译文、复制、固定、关闭。语言、解释、朗读、生词、重试和设置放在次级操作区。
- 路由信息使用安静的文本状态，例如“本地 OCR · Gemini 文本翻译”或“免费在线翻译”；不是一排装饰性徽章。

### 3.2 结果浮窗

- 状态只有：获取原文、识别、翻译、成功、部分成功、失败、已取消。
- Escape 第一次即执行用户可预测的动作：请求中则取消并保留面板；空闲则关闭。不要让相同状态下需要猜测按几次。
- 失败信息说明“发生什么、数据是否已发送、下一步是什么”。
- 首次可能上传截图时进行一次明确授权；之后仍可在结果中看到上传目标。
- “展开”必须把当前 `TranslationSession` 带到完整工作表面，而不是重新翻译或丢失上下文。

### 3.3 控制中心

建议导航不超过五项：

1. 通用：启动、主题、浮窗行为、语言默认值。
2. 快捷键：选词、截图、快速输入、关闭；冲突实时显示。
3. 服务：Provider Profile 列表与默认文本/视觉服务。
4. OCR 与隐私：本地 OCR 状态、出网策略、截图上传规则、历史保存。
5. 数据与高级：历史/生词管理、导出、日志、代理/自定义 Endpoint/TLS。

历史和生词不是“设置项”。它们可作为独立资料库页面从控制中心进入，但不要与开关、Endpoint 输入框使用相同布局语义。

## 4. 供应商与隐私重构

### 4.1 新数据模型

把当前单个 `ProviderSettings` 拆成：

```text
ProviderProfile
  id                  稳定 UUID
  displayName         用户可编辑名称
  providerKind        OpenAI / Anthropic / Gemini / OpenAI Compatible
  protocol            具体协议能力
  baseUrl/endpoints   高级配置
  textModel           可空
  visionModel         可空
  capabilities        text / vision / streaming / tts
  credentialRef       Windows Credential Manager 中的独立引用
  connectionState     unknown / testing / ready / failed

TranslationPreferences
  defaultTextProfileId
  defaultVisionProfileId
  defaultLanguagePair
  explanationPolicy
  protectCodeTokens

OutboundPolicy
  OfflineOnly
  LocalServicesOnly
  OnlineTextAllowed
  OnlineTextAndConfirmedImages
```

“联网开关”“安全离线模式”“允许自动上传图片”不应是三个可能互相矛盾的布尔值。用一个明确的出网策略，加上首次图片授权，才能覆盖真实用户心智。

### 4.2 服务页流程

服务页首页是配置列表，不是巨大表单：

- 每行显示名称、协议、文字/视觉能力、默认角色和最近连接状态。
- “添加服务”进入四步向导：选择服务类型 → 凭据/地址 → 模型与能力 → 测试并确认。
- “测试连接”只测试当前草稿，不保存；成功后用户再点击“添加”或“保存”。
- API Key 每个 Profile 独立存储。删除 Key 或删除 Profile 需要确认，并说明是否会回退到免费在线服务。
- 免费在线引擎作为一个真实、可见的内置 Profile，标明“会把文本发送到 Google 公共翻译服务”，首次启用需确认。
- Base URL、Endpoint、Header、TLS 放进“高级”，常见厂商不显示无关字段。
- 模型预设是可更新的建议，不是写死的产品真相；允许用户输入自定义模型。

### 4.3 请求决策只能有一个入口

所有窗口必须调用：

```text
TranslationCoordinator.StartAsync(TranslationRequest, CancellationToken)
```

Coordinator 负责：

- 读取不可变配置快照；
- 检查出网和图片上传策略；
- 选择 OCR 与 Provider；
- 保护并恢复代码 Token；
- 发出请求级 ID；
- 写入统一诊断和历史；
- 产出 `TranslationSession` 状态。

任何 Window、ViewModel 或托盘处理器都不得再直接调用 `FreeTranslateService`、凭据存储或自行解释安全模式。

## 5. 目标代码架构

### 5.1 分层

```text
PopGlot.Windows.Views
  只处理布局、焦点、窗口位置和 Win32 交互

PopGlot.Windows.ViewModels
  QuickTranslateViewModel / ResultPanelViewModel / SettingsViewModel

PopGlot.Application
  TranslationCoordinator / ProviderProfileService / SettingsService
  HistoryService / VocabularyService / PrivacyPolicyService

Rust Core
  Provider 协议、路由纯函数、Token 保护、响应解析、传输限制

FFI Contract
  版本化 DTO、request_id、错误码、契约测试
```

不要一次性把所有 code-behind 机械搬成 ViewModel。迁移顺序应沿用户旅程：先统一翻译会话，再迁供应商草稿，再拆设置页，最后处理历史和生词。

### 5.2 会话状态

```text
Created -> AcquiringInput -> OcrRunning -> Routing -> Translating
        -> Completed | Partial | Failed | Cancelled
```

`TranslationSession` 至少保存：请求 ID、输入来源、原文、语言对、当前阶段、路由决策、Provider Profile、结果、警告、Token 校验、是否出网/上传、各阶段耗时和错误恢复动作。

同一个会话可被多个 View 展示，但只有 Coordinator 推进状态。这样可以消除主窗口、极速查词和浮窗各写一套状态机的问题。

### 5.3 请求级取消

- FFI 的开始请求返回 `request_id`。
- 取消 API 必须接收 `request_id`，只取消对应 token。
- 结束旧请求不得清理新请求状态。
- 增加 A/B 并发测试：启动 A、启动 B、取消 A，B 必须继续；反向同样成立。
- 在架构完成前若产品只允许一个前台请求，必须由 Coordinator 的显式策略串行化，而不是依赖“最后一个全局 token”。
- Rust Core 的锁只用于复制不可变配置和 Provider client handle，网络往返前必须释放；UI 保存设置不得等待网络读锁。

FFI v2 同时补齐结构化合同：请求返回 `abi_version`、`request_id` 和结构化错误 `code/message/retryable/status_code`；草稿校验与草稿连接测试是只读 API。截图参数使用 `pointer + length`，避免在 C#/JSON/Rust 之间制造 base64 大副本。C# 与 Rust 手工镜像 DTO 必须有契约快照测试，后续再评估由同一 schema 生成。

### 5.4 设置与本地数据

- 所有 JSON 设置使用“写临时文件 → flush → 原子替换 → 保留最近一个备份”。
- 配置损坏时保留坏文件并显示恢复提示，不能静默当作第一次启动。
- 生词存储改为原子写入、有限条数/大小、异步 IO，并应用与历史相同的敏感信息过滤规则。
- 当前数据量下无需急于引入 SQLite；先把原子性、边界和接口做好。只有在历史/生词规模、查询或并发写入超出 JSON 能力时再迁移。

### 5.5 启动路径

- 启动只创建单实例、托盘、主题和轻量消息窗口，完成快捷键注册。
- 不为注册快捷键而提前构造完整 `MainWindow`。
- 主窗口、历史、生词、OCR 状态和重型资源在首次使用时按需加载；可在托盘就绪后低优先级预热 Rust runtime。
- 删除 UI 线程上的 `Thread.Sleep`；剪贴板重试使用异步延迟或后台线程，并给出总超时。
- 截图抓屏、缩放和 PNG 编码移出 Dispatcher；OCR 与视觉上传使用各自合适的尺寸，默认限制到 8 MP，并记录捕获、编码、字节数和内存峰值。
- TTS 使用单一 generation/CTS；停止朗读要同时取消播放器与仍在合成的网络/本地任务，启动时清理遗留临时文件。

## 6. 去除“AI 味”的 UI 规则

### 6.1 当前“AI 味”的来源

- 每层都使用大圆角卡片，卡片里再嵌卡片；缺少真正的信息层级。
- 预设、状态、能力和动作都做成胶囊按钮/徽章，视觉语义不区分。
- 大标题、解释性文案、装饰图标和空白很充足，但核心任务的控件关系松散。
- 一个页面试图把所有高级能力“展示出来”，像功能演示页而不是成熟设置工具。
- 通用字母 P、绿色渐变/阴影和圆角组件缺少产品识别，也没有贴近 Windows 工作流。

### 6.2 新设计约束

1. 采用 4/8 间距网格；主要内容宽度受控，不以巨大空白制造“高级感”。
2. 设置页默认使用扁平分组行和分隔线；只有真正独立的对象（Provider Profile、错误摘要）使用卡片。
3. 圆角分三级且克制：输入/按钮小圆角，浮窗中圆角，不在每个容器上叠加大圆角。
4. 一个表面最多一个主按钮。次要动作使用文本按钮、菜单或图标加可访问名称。
5. 使用 Segoe UI 与系统中文回退；字号层级少而稳定，正文不靠浅灰小字承担关键含义。
6. 只使用一个强调色。成功、警告、失败同时提供图标和文本，不仅靠颜色。
7. 动效只解释状态变化；尊重系统“减少动画”和高对比度设置。
8. 删除“智能、极速、专业、无缝”等无法由当前状态证明的文案；状态文案说明事实。
9. 优先使用原生窗口阴影、圆角和菜单。`AllowsTransparency` + 大 `DropShadowEffect` 仅保留给确有必要的遮罩窗口。
10. 图标形成一致的 16/20 px 线性系统；托盘与应用图标重新设计，不继续使用通用字母徽标作为最终品牌。

### 6.3 可访问性门槛

- 每个交互控件有可读名称；图标按钮提供 `AutomationProperties.Name`。
- 所有核心旅程可只用键盘完成，焦点顺序与视觉顺序一致，焦点环不可被样式清空。
- 在 100%、125%、150%、200% DPI 下无裁切；最小窗口仍能操作保存/取消。
- 高对比度下保留状态、边界和焦点；颜色不是唯一信息渠道。
- 屏幕阅读器能读出请求状态、出网目标、错误和 Token 完整性警告。
- 触控/鼠标点击目标不小于 32 px，高频关键目标优先 40 px。

## 7. 性能与可靠性预算

第一小时先在 Release x64、固定机器上记录基线。下面是目标门槛；若现状更优，则以现状为基线只允许回归 10%。

| 指标 | 目标 |
|---|---|
| 冷启动到托盘/快捷键可用 p95 | ≤ 1.5 s |
| 热启动到托盘可用 p95 | ≤ 0.8 s |
| 快捷键到结果壳首次绘制 p95 | ≤ 150 ms |
| 输入/点击引起的 UI 主线程阻塞 | 单次 < 50 ms |
| 取消动作到 UI 显示已取消 | ≤ 100 ms |
| 取消动作到 Provider 请求终止 p95 | ≤ 500 ms，受外部协议限制时记录 |
| 托盘空闲 Working Set（设置未打开，30 s 后） | ≤ 100 MiB 或比基线降低 ≥ 30% |
| 隐藏窗口持续 CPU | 接近 0%，无轮询唤醒 |
| 配置/历史/生词故障注入 | 不产生不可恢复的半文件 |
| 4 MP 截图抓取 + 编码 p95 | ≤ 300 ms |
| 8 MP 截图瞬时额外内存 | ≤ 96 MiB |
| 浮窗打开/关闭 100 次后的不可回收增长 | ≤ 10 MiB |

观测字段统一写入本地诊断：request_id、source_kind、route、provider_profile_id、stage timings、status、cancelled、fallback、token_integrity。不得记录 API Key、完整截图或默认记录完整原文。

## 8. 优先级与验收标准

### P0：在任何视觉重写前完成

1. **隐私策略单入口**：任何入口在 `OfflineOnly` 下均不能触发 DNS/HTTP；加入网络替身测试。
2. **快捷键穷尽处理**：所有 `HotkeyAction` 有行为和测试；保存设置不丢任何绑定。
3. **测试连接无副作用**：测试草稿成功/失败都不改变磁盘配置、活动配置或 Credential。
4. **请求级取消**：A/B 并发取消互不影响。
5. **免费引擎显式化**：首次出网确认、设置页可见、结果页显示来源；拒绝后不自动回退。
6. **配置原子写入**：中断/损坏测试可恢复；坏文件保留并提示。
7. **关键动作闭环**：浮窗展开、导出格式、清除 Key、错误跳转与文案一致。
8. **文档与实际默认值一致**：历史数量/大小/期限、网络默认行为、截图上传策略只有一个真相来源。
9. **隐私迁移收紧**：旧配置缺字段时不得自动获得联网或图片上传权限；迁移矩阵覆盖所有历史 schema。
10. **网络不持有 Core 全局锁**：翻译进行时读取/保存设置不会等待网络超时，UI 不阻塞。

### P1：形成新的产品骨架

1. 建立 `TranslationCoordinator` 和 `TranslationSession`，三个入口不再直接调用 Provider。
2. 建立 Provider Profile + 独立 Credential 引用与旧配置迁移。
3. 合并极速查词与主窗口文本翻译；资料库与控制中心分离。
4. 供应商配置改成列表 + 向导 + 草稿测试。
5. 主窗口延迟创建，历史/生词/OCR 状态按需加载。
6. 生词原子、有限、敏感信息过滤；导出格式与扩展名一致。
7. 核心控件补齐键盘、自动化名称、高对比和 DPI 验证。
8. 加入请求级性能埋点和基线脚本。
9. CI 实际运行 Windows Shell 逻辑测试，并加入 FFI 并发、WPF 启动/主旅程 smoke；不能只做 Release build。

### P2：完成体验与扩展

- 统一设计 Token 与控件库，清除旧样式和重复资源。
- 结果浮窗细节、窗口定位、多屏/DPI、TTS 生命周期、焦点丢失策略完善。
- 视觉回归矩阵：浅/深/高对比 × 100/125/150/200% DPI × 中文/英文长文本。
- 评估多服务并排翻译、插件、剪贴板监听、外部接口；每项必须先有真实用户任务与性能/隐私预算。

## 9. 首个 24 小时执行方案

24 小时指持续集成窗口，不代表可以安全完成全部重写。第一轮成功标准是：P0 风险封闭、目标架构接缝落地、一个新 UI 纵向切片可用、测试和性能基线可信。

### 0–1 小时：冻结基线

- Orchestrator 保存当前截图、关键旅程录屏、Release 启动/内存基线和 `verify.ps1` 输出。
- 建立任务所有权表和独立 worktree；标记当前未提交工作，不做清理。
- 冻结新增功能，确认 P0 列表与接口命名。

验收：每个 Agent 知道自己可修改的目录；基线结果可复现。

### 1–5 小时：并行封闭 P0

- Agent A：安全策略、免费引擎同意、QuickSearch 统一调用。
- Agent B：快捷键穷尽分支、保存字段、展开动作、导出文案/格式。
- Agent C：请求级取消、并发测试、原子设置写入和损坏恢复。
- Orchestrator：补用户旅程验收表，持续合并小提交。

验收：离线零出网；热键无异常；测试连接无持久化；A/B 取消测试通过。

### 5–9 小时：建立应用层接缝

- 定义 `TranslationRequest`、`TranslationSession`、`TranslationCoordinator`。
- 先迁移“手动输入”纵向切片，再迁移 QuickSearch；截图入口保留适配层。
- 为旧 CoreBridge/FreeTranslateService 加禁止直接调用的边界测试或代码审查规则。

验收：两个文本入口走同一 Coordinator，同一隐私矩阵和同一历史写入逻辑。

### 9–14 小时：重做信息架构和供应商纵向切片

- 建立新的控制中心导航骨架。
- 完成服务列表与“添加 OpenAI Compatible 服务”一条完整向导；其他厂商暂走相同协议适配，不追求一次铺满。
- 测试草稿、保存、设为默认、删除凭据形成闭环。
- 用真实长模型名、失败消息、无 Key、本地服务地址做布局压力测试。

验收：普通用户不打开高级区即可完成添加服务；测试不保存；可明确看到默认文字/视觉服务。

### 14–18 小时：统一快速翻译表面

- 合并快速输入与主翻译工作台的状态模型。
- 简化结果浮窗首层操作；接通展开并携带当前会话。
- 清除嵌套卡片、无意义徽章和重复标题；保留一个主动作。

验收：选词、输入、截图结果使用同一状态语言；用户两秒内能看出结果来源与数据是否出网。

### 18–21 小时：性能与可访问性

- 主窗口延迟构造；移除 UI 线程 Sleep；按需加载资料库和 OCR 状态。
- 补自动化名称、焦点环、Tab 顺序；检查 200% DPI 和高对比。
- 复测启动、Working Set、快捷键到首帧和取消延迟。

验收：性能达到预算或有数据支持的剩余差距；核心旅程可纯键盘完成。

### 21–24 小时：集成与发布门槛

- 全量 `verify.ps1`、隐私矩阵、并发取消、配置故障注入、视觉矩阵抽样。
- CI 补齐 Windows Shell 逻辑测试、FFI 契约/并发测试和 Release smoke；本地通过但 CI 未执行的测试不算门禁。
- 删除死代码和已被替换的重复入口，但仅在引用和回归测试证明安全后进行。
- 更新架构、隐私、配置迁移和用户文档；生成剩余 P1/P2 backlog。

验收：主分支可构建、测试全绿、无 P0 未解释；新旧配置可迁移和回滚。

## 10. Agent 分工与协作协议

### 10.1 推荐角色

- **Orchestrator / 产品架构 Agent**：守产品契约、任务拆分、接口合并和最终验收；尽量不与实现 Agent 争抢同一文件。
- **隐私与核心 Agent**：Rust domain/core/ffi、请求 ID、策略矩阵、原子配置。
- **WPF 应用层 Agent**：Coordinator、ViewModel、快捷键、启动路径、数据服务。
- **产品 UI Agent**：XAML、信息架构、供应商向导、浮窗交互和可访问性。
- **质量 Agent**：旅程测试、故障注入、性能基线、DPI/高对比、发布清单。

若只有四个并行槽，Orchestrator 不做大面积 UI 实现；质量工作可由各实现 Agent 先写测试，再由 Orchestrator 交叉验收。

### 10.2 强制规则

1. 每个 Agent 使用独立 worktree 和 `codex/<task>` 分支；一张任务卡一个小提交序列。
2. 开始前声明文件所有权；同一波次不允许两个 Agent 同改 `MainWindow.xaml(.cs)`、`App.xaml.cs` 或 FFI 合同。
3. 先写失败测试或可复现步骤，再改实现；合并说明必须包含用户影响和验收结果。
4. 不做全仓库格式化、不升级无关依赖、不重写用户未提交代码、不用 reset/checkout 丢弃冲突。
5. 每 90 分钟做一次集成；合并后立即运行相关测试，4 小时至少一次全量验证。
6. Agent 遇到产品选择时引用本文的用户承诺；若仍有冲突，停止扩张范围，由 Orchestrator 决策并记录 ADR。
7. 任何“更智能”的行为必须能解释、能测试、能关闭；任何自动出网或上传必须先通过隐私矩阵。

### 10.3 每张任务卡模板

## 11. 发布验收清单
