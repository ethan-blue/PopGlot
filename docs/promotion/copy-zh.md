```
最近一直在跟英文报错、注释和文档打交道。之前一直在用的 Pot，官方仓库已经归档了，主仓库最后一次提交停在 2026-07-04。之后我找了一圈替代，没找到顺手的，就自己写了一个，放在 GitHub 上：

https://github.com/ethan-blue/PopGlot

先说清楚：现在还是 0.1.x，功能收得很窄——划词翻译、截图翻译、查词、一个左右分栏的工作台。没有账号系统，没有同步，没有手机端，也没有 macOS / Linux 版。

做了三件我自己最在意的事。

一、划词不抢剪贴板。

大部分划词工具靠模拟 Ctrl+C 拿选中文本，问题出在「拿完之后」：要么不还原，要么无脑还原。如果你在翻译的间隙又复制了别的东西，那一下就会被覆盖掉。

我的做法是给整段操作记序列号（GetClipboardSequenceNumber）：进入时抓一份完整的剪贴板快照，发 Ctrl+C 之前记一个号，复制完成后再记一个号；只有在「最后一次写入确实是我这次复制」的时候才还原快照。中间你要是复制了新东西，序列号变了，我就不动它。

两个配套的细节：一是读取剪贴板格式失败时直接放弃本次划词，而不是拿一份空快照去还原——那等于把你的剪贴板清空；二是按完 Ctrl+Alt+W 你的手指可能还压着 Alt，这时候发 Ctrl+C 会变成 Ctrl+Alt+C，大部分程序不认，所以会先等修饰键抬起来再发。所有剪贴板操作都丢到一个独立的 STA 线程上做，带超时和重试，被剪贴板管理器卡住也不会冻住界面。

二、截图默认在本机做完。

截图翻译有两条路：先本机 OCR 出文字再翻译，或者把整张图交给视觉模型。后者效果好，但图要离开本机。

默认的 Auto 模式里，「图片外发」是一个独立开关，默认关。关着的时候就是本机 OCR 出文字、文本模型翻译。你也可以显式选「视觉识别 + 文本翻译」（视觉模型只做转录，翻译仍走文本模型）或者「视觉直译」。选了哪种、图有没有离开本机，界面上会写明。开「安全离线模式」之后，包括免费线路在内的所有外发请求都不发，本机模型地址（Ollama、LM Studio）还能用。

三、工作台里译文和要点是分开的。

有些工具点了「总结」译文就没了。这里左边原文右边译文，译文下面是说明，「要点」是单独一栏，不会互相覆盖。

引擎支持 OpenAI 兼容、OpenAI Responses、Anthropic、Gemini，以及 Ollama、LM Studio 这种本机地址。密钥存 Windows 凭据管理器，日志不记原文、截图和密钥。

几个必须提前说的坑：

- 需要自备 API Key。没配自己的引擎时默认走 Google 公共翻译，Google 不通可以切 MyMemory——这是公共翻译质量，就是「能看懂」的水平，别指望它对技术文档翻得多好。一次只发你选中的那一条。
- 安装包目前没有签名。第一次运行大概率会看到 Windows SmartScreen 的蓝色提示，点「更多信息 → 仍要运行」就行。校验用发布页每个包附的同名 .sha256：
  (Get-FileHash -Path .\PopGlot-v0.1.35-win-x64-setup.exe -Algorithm SHA256).Hash.ToLower()
- 只做 Windows 10/11 x64。
- 以管理员权限运行的程序（受 UIPI 隔离）收不到模拟按键，这种情况要么用管理员身份跑 PopGlot，要么手动复制后在浮窗里粘贴。

下载在 Releases：https://github.com/ethan-blue/PopGlot/releases
安装包 PopGlot-v0.1.35-win-x64-setup.exe（约 59 MB），便携 zip（约 88 MB），两个都自带 .NET，不用另装运行时。

代码是 MIT。结构是 WPF(.NET 10) 外壳 + Rust 内核，中间用 C ABI 分开——外壳可以换，翻译内核不用跟着重写。

现在最缺的是真实场景的反馈，尤其是「在某某程序里划词没反应」这类。直接开 issue 就行，我基本当天能看。
```

#### 用 C ABI 把 WPF 和 Rust 分开：一个 Windows 翻译工具的三个实现细节

PopGlot 是一个 Windows 上的划词 / 截图翻译工具，代码在 https://github.com/ethan-blue/PopGlot ，MIT。这篇文章不讲它有多少功能，讲三个做的时候踩得比较狠的点：跨语言分层、划词的剪贴板还原、截图的两条处理路径。

## 一、分层：外壳可以换，内核不跟着重写

一开始的念头很简单：翻译这件事（拼请求、流式解析、路由、重试、历史）和「Windows 上怎么弹出一个窗口」没有关系。把它们混在一起，换一个 UI 框架就等于重写一遍。

所以代码分成四块：

```
apps/PopGlot.Windows   WPF(.NET 10) 外壳：窗口、快捷键、剪贴板、托盘
crates/popglot-domain  领域类型：翻译模式、引擎配置、消息结构
crates/popglot-core    翻译与路由：provider、流式、重试、历史
crates/popglot-ffi     C ABI 层，编译产物 popglot_ffi.dll
```

外壳只通过 `popglot-ffi` 导出的 C ABI 调内核，不直接依赖 `popglot-core`。带来的好处是职责清晰：所有平台相关的东西（剪贴板、SendInput、凭据管理器）都被限制在 `apps/PopGlot.Windows` 里，Rust 侧完全不知道自己跑在什么系统上。

代价也要说清楚：C ABI 是一层手写的边界，结构体布局和字符串所有权都要自己管，加一个字段要改两边。如果项目规模很小，这层是纯负担。它划算的前提是「内核确实要长期活下去、外壳可能换」。

构建时 WPF 工程会自己编译 `popglot-ffi` 并把 `popglot_ffi.dll` 拷到输出目录，所以本地只需要：

```powershell
./scripts/verify.ps1   # Rust fmt + test + clippy + WPF 构建 + 连接场景
./scripts/run.ps1
```

`verify.ps1` 里的测试全部使用隔离配置与模拟服务，不会打到真实模型。

## 二、划词：剪贴板怎么还原才不算「抢」

Windows 上没有统一的「获取当前选中文本」的 API。划词工具通用做法是三段：抓当前剪贴板 → 模拟 Ctrl+C → 读文本 → 还原剪贴板。

麻烦全在「还原」这一步。

**坑 1：无脑还原会覆盖用户的新复制。**

翻译从发起到出结果有网络往返，这段时间里用户完全可能按了 Ctrl+V 之外的操作、复制了新东西。如果结束时不看情况直接 `Restore`，就把用户的新内容盖掉了。

解决办法是给剪贴板操作记序列号。`user32.dll` 的 `GetClipboardSequenceNumber()` 每次剪贴板内容变化都会自增：

```csharp
var sequenceBeforeCopy = _clipboard.SequenceNumber;   // 发 Ctrl+C 之前
await _clipboard.SendCopyAsync(cancellationToken);

// 轮询等待目标应用真的响应了这次复制
var deadline = DateTime.UtcNow + CopyTimeout;         // 1000 ms
while (DateTime.UtcNow < deadline)
{
    if (_clipboard.SequenceNumber != sequenceBeforeCopy)
    {
        copiedSequence = _clipboard.SequenceNumber;
        break;
    }
    await Task.Delay(15);
}
```

还原只在一个条件下发生——**本次复制仍然是剪贴板上最新的一次写入**：

```csharp
finally
{
    // 只有我们的合成复制还是最新写入时才还原；
    // 事务期间任何一次真实的用户写入都优先。
    if (copiedSequence is not null && _clipboard.SequenceNumber == copiedSequence.Value)
    {
        await _clipboard.RestoreAsync(snapshot);
    }
}
```

**坑 2：快照抓取失败时，空快照会把剪贴板清空。**

如果 `Clipboard.GetDataObject()` 或遍历格式时抛异常，最省事的做法是「当作空剪贴板，后面 Restore 时 Clear 一下」。这正好是最坏的结果：用户原来的内容被清掉了。

所以抓取是 fail-closed 的——任何一个格式读不出来就直接抛异常，**在发送 Ctrl+C 之前**中止，而不是带着一份残缺快照继续。

```csharp
var data = source.GetData(format, autoConvert: false);
if (data is null)
{
    throw new InvalidOperationException(
        $"剪贴板格式“{format}”无法完整读取；为保护原内容，本次划词已取消。");
}
```

快照要能安全复制回来，所以每种格式都要深拷贝。能处理的类型是有限的几个：`string`、`string[]`（文件列表）、`byte[]`、`MemoryStream`、`Bitmap`、`BitmapSource`、以及任意值类型。遇到不在白名单里的格式，同样直接放弃这次划词——宁可翻译不成，也不能猜。

**坑 3：你的手指还压着 Alt。**

划词快捷键是 `Ctrl+Alt+W`。按键松手有先后，如果 `W` 抬起之前整个组合的 Alt 还处于按下状态，这时候发 `Ctrl+C`，目标应用收到的是 `Ctrl+Alt+C`——大多数程序直接忽略。

所以发键之前要等修饰键抬起来，而且这个等待本身必须是可取消的：

```csharp
var deadline = Environment.TickCount64 + ModifierWaitBudgetMilliseconds; // 500 ms
while (Environment.TickCount64 < deadline)
{
    cancellationToken.ThrowIfCancellationRequested();
    if (!anyModifierDown()) break;
    await Task.Delay(modifierPollDelay, cancellationToken); // 10 ms
}
cancellationToken.ThrowIfCancellationRequested();  // 发键前最后一个检查点

// 先给仍按住的修饰键补 KeyUp，再发一个干净的 Ctrl+C
foreach (var modifier in captureModifiersToRelease())
{
    inputs.Add(KeyboardInput(modifier, KeyeventfKeyup));
}
inputs.Add(KeyboardInput(VkControl, 0));
inputs.Add(KeyboardInput(VkC, 0));
inputs.Add(KeyboardInput(VkC, KeyeventfKeyup));
inputs.Add(KeyboardInput(VkControl, KeyeventfKeyup));
```

注意 Ctrl 不在「补 KeyUp」的列表里——它会在下面的组合里重新按下，保证发出的是纯粹的 `Ctrl+C`。

「可取消」这件事比看上去重要。合成按键是一次性副作用：一旦 Ctrl+C 真的发了出去，就必须等到它落地并把剪贴板还原完，否则这次复制就会泄漏成用户剪贴板上的内容。所以每个等待点都是一个取消检查点，预算耗尽时**在按键发出之前**中止；而按键一旦发出，即使收到取消也要把观察走完。

**坑 4：剪贴板会把 UI 线程卡死。**

`Clipboard.GetDataObject()` 是一次 OLE 调用。远端桌面、Office、第三方剪贴板管理器做延迟渲染时，这个调用可以卡好几秒——在 UI 线程上直接冻结整个窗口。

处理办法是把它丢到专用的 STA 工作线程上，用一个信号量串行化（同一时刻只跑一个剪贴板操作），并加超时：

```csharp
if (!await ClipboardWorkerGate.WaitAsync(TimeSpan.FromMilliseconds(100)))
{
    throw new InvalidOperationException(
        "上一次剪贴板操作仍未响应，已取消本次划词。请关闭占用剪贴板的程序后重试。");
}
// 超时了也不能在中途放开门禁：一次卡住的 OLE 调用无法在进程内安全取消，
// 提前放开门禁只会让卡死的 STA 线程越堆越多。门禁只能由工作线程自己释放。
```

重试策略也分了两类：`COMException` / `ExternalException` 重试 6 次，间隔递增；`TimeoutException` 一次都不重试，直接失败——重试只会叠加更多卡住的线程。

**坑 5：UIPI。**

以管理员权限运行的窗口收不到普通进程发来的 `SendInput`（`ERROR_ACCESS_DENIED`，错误码 5）。这种情况不要静默失败，直接告诉用户原因：要么用管理员身份跑 PopGlot，要么手动复制后在浮窗里粘贴。

## 三、截图：本机 OCR 和视觉直译之间怎么分

截图翻译有两条路：

- **本机 OCR**：Windows OCR 出文字 → 文本模型翻译。图不出本机，但需要系统装了对应语言的 OCR 包。
- **视觉模型**：整张图交给多模态模型。效果好，但图离开本机。

第三条路是两者的组合：**视觉模型只做转录，翻译仍然交给文本模型**。这样做的好处是译文风格和术语可以沿用你已经调好的文本引擎（甚至是本机的 Ollama），而不是被视觉模型的输出风格绑死。

所以模式一共有四种：

```rust
pub enum TranslationMode {
    #[default]
    Auto,          // 自动：按可用性和授权决定
    LocalOcr,      // 显式本机 OCR
    VisionDirect,  // 视觉模型直接识别并翻译
    VisionOcr,     // 视觉模型只转录，译文由文本模型生成
}
```

设计上有两条硬规则：

**规则一：图片外发是一个独立开关，默认关。** 在 `Auto` 模式下，只有用户显式授权 `allow_image_upload_in_auto`，图片才可能离开本机；没授权就走本机 OCR。这个开关和 `network_enabled` 一样，反序列化时**缺失视为 false**，而不是用 `#[serde(default)]` 兜底——因为老版本配置文件升级上来时，用户从来没有显式给过这个授权，不能替他给。

**规则二：不做静默降级。** 用户显式选了 `VisionDirect` 但视觉服务不可用，就明确报错并说明原因，而不是悄悄退回 OCR。用户选了一条路，工具就不该替他换一条。同理，`VisionOcr` 要求图片模型和文字模型同时存在，缺一个就告诉用户缺哪个。

选了什么、图有没有离开本机，会在结果里写明一句人话，例如：

- 「已按设置使用本地 OCR；截图不会上传给视觉模型。」
- 「已授权局域网视觉模型直接识别并翻译截图（截图将发送到局域网另一台设备）。」

再加上「安全离线模式」：打开后包括免费线路在内的所有外发请求都不发出，本机模型地址仍可用。

## 四、剩下的一些取舍

- **密钥**存 Windows 凭据管理器，条目名 `PopGlot/provider/<引擎 id>`，不进配置文件。日志不记原文、截图、密钥。
- **原文**只在用户选中的那一刻发出去，一次一条。

## 我的划词翻译工作流：为什么最后自己写了一个

我每天大概有一半时间在跟英文打交道：报错信息、库的 issue、别人的注释，还有一些没有中文版的文档。划词翻译是我打开次数最多的那类工具，也大概是换得最频繁的一类——不是因为不好用，而是总有一两个地方让我用着不放心。

后来我把自己真正在意的事列了出来，发现其实只有三条。再往后就变成了 PopGlot（https://github.com/ethan-blue/PopGlot ），MIT 开源，Windows 10/11 x64。

先说这三条，再说它现在还不做什么。

### 第一条：别动我的剪贴板

这是最让我不安的一条。

划词翻译要拿到你选中的文字，通常的做法是模拟一次 Ctrl+C，读完再还原剪贴板。听起来没问题，但「还原」这一步藏着两个坑：

一是**不还原**。翻译完，剪贴板上就变成了你刚才选中的那段英文。你可能半小时后按 Ctrl+V 才发现。

二是**无脑还原**。如果你在翻译还没出结果的时候又复制了别的东西，工具结束时会把剪贴板「还原」成半小时前那份——你刚复制的内容没了。

第二种比第一种更难受，因为它随机发生，你很难意识到是翻译工具干的。

我现在用的做法，是用 Windows 剪贴板的序列号（`GetClipboardSequenceNumber()`，内容每变一次就自增）给这整段操作做标记：进的时候记一个号，发完 Ctrl+C 再记一个号，只有在「最后一次写入确实是我这次复制」的时候才还原。中间你要是复制了新东西，序列号变了，那这次就不还原，你的新内容留着。

还有一个更隐蔽的分支：如果读取剪贴板内容时出错了怎么办。最省事的写法是「当作空的，结束的时候清一下」，而那正好会把你原来的内容清掉。所以这里做的是**读不出来就直接放弃这次划词**，在发 Ctrl+C 之前就停，而不是带着一份残缺的备份继续走。

我后来在测试里确认过一次：开着翻译工具翻译一整段，中间随手复制一个文件路径，翻译出结果，剪贴板上还是那个文件路径。这件事现在稳定了。

### 第二条：截图默认不要离开本机

划词能解决大部分问题，但有些文字划不出来——图片里的报错弹窗、终端里某个 GUI 工具的输出、PDF 扫描件。这时候要截图翻译。

截图翻译有两条路：

- **本机 OCR**：系统自带的 OCR 把图上的字认出来，再交给文本模型翻译。图不出本机。
- **视觉模型**：把整张图发给多模态模型，它自己认自己翻。效果通常更好，但图离开本机。

我的选择不是二选一，而是：**把「图片外发」做成一个独立的开关，默认关**。关着的时候就是本机 OCR。你觉得某张图值得用视觉模型，再单独开。开了之后，界面上会明说这张图去哪了——发给外网、发给局域网里另一台跑 Ollama 的机器、还是根本没离开本机，三种情况写得不一样。

还有个兜底开关叫「安全离线模式」。打开之后，包括免费翻译线路在内的所有外发请求都不发。本机模型地址（Ollama、LM Studio）还能用——因为我理解的「离线」是「不出我的机器」，不是「不许用模型」。

一个我认为很重要的小规则：**不做静默降级**。我显式选了视觉模型但服务不通时，它会明确告诉我「不可用，原因是 XXX」，而不是悄悄退回本机 OCR。工具不该替我换一条我没选的路。

### 第三条：译文和要点别互相覆盖

这条听起来很小，但踩过一次就忘不掉。

不少翻译工具会在同一块区域里放译文，再放一个「总结 / 要点」按钮。你点了要点，译文就没了。而大多数时候我要的是「先读懂大意，再回去看准确译文」——这两个是要同时在的。

所以工作台做成了：左边原文，右边译文，译文下面是说明；「要点」是单独的一栏，点它不会动译文。

### 它现在还不做什么

写这部分比写功能列表重要。

- **只支持 Windows 10/11 x64。** 没有 macOS 和 Linux 版。
- **需要自备 API Key。** 支持 OpenAI 兼容、OpenAI Responses、Anthropic、Gemini，以及 Ollama、LM Studio 这类本机地址。密钥存在 Windows 凭据管理器里，日志不记原文、截图和密钥。
- **没配自己的引擎时，默认走 Google 公共翻译**，Google 不通可以切 MyMemory。这是公共翻译的质量——看个大意没问题，指望它把一段技术文档翻得准确是不现实的。一次只发你选中的那一条，不会整段整段往外传。
- **安装包目前没有签名。** 第一次运行会看到 Windows SmartScreen 的提示，点「更多信息 → 仍要运行」即可。介意的话可以下便携 zip 解压运行，或者用发布页附带的同名 `.sha256` 自己校验。
- 没有账号系统，没有同步，没有手机端。

### 我现在怎么用它

大部分时候就是按 `Ctrl+Alt+W` 划一段，看一眼，按 `Ctrl+Alt+X` 关掉浮窗。读长文档时用 `Ctrl+Alt+O` 打开工作台，左边贴原文右边看译文，要点那一栏留到最后看。碰到划不出来的文字用 `Ctrl+Alt+Space` 框选。临时想查一个词用 `Ctrl+Alt+Q`。

它现在的样子，大概就是「一个不会给我添麻烦的划词翻译」。我没有打算把它做成一个大而全的平台——能少一次「咦我的剪贴板呢」，就已经值了。

下载在 https://github.com/ethan-blue/PopGlot/releases ，安装包约 59 MB，便携 zip 约 88 MB，两个都自带 .NET，不用另装运行时。

## 模板 A：原理型（回答「划词翻译是怎么实现的」这类问题）

```
Windows 上没有统一的「获取当前选中文本」的 API，所以划词翻译工具普遍走四步：抓剪贴板快照、模拟 Ctrl+C、读文本、还原剪贴板。前两步和后一步看着简单，工程上的麻烦基本都在「还原」这一步。

**一、还原时机的判断**

直接 Restore 会出问题：翻译有网络往返，这段时间里用户可能复制了新东西，无脑还原就会把它盖掉。

常见做法是用 GetClipboardSequenceNumber()（每次剪贴板内容变化自增）做标记：发 Ctrl+C 前记一个号，复制完成后再记一个号，只有「最后一次写入确实是本次合成复制」时才还原。用户的写入永远优先。

**二、快照抓取失败的处理**

GetDataObject() 或遍历格式时抛异常，最省事的写法是「当作空剪贴板，最后 Clear 一下」——而这正好把用户原来的内容清掉了。正确的做法是 fail-closed：任何一个格式读不出来就中止，而且要在发 Ctrl+C **之前**中止，不要带着残缺快照继续。

快照要能安全写回，每种格式都要深拷贝（string、文件列表、byte[]、MemoryStream、Bitmap、BitmapSource 等），遇到处理不了的格式宁可放弃这次划词。

**三、修饰键还没松开**

如果划词快捷键是 Ctrl+Alt+W，按键松开有先后：Alt 还按着的时候发 Ctrl+C，目标应用收到的是 Ctrl+Alt+C，多数程序直接忽略。所以要先补发 Alt / Shift / Win 的 KeyUp，再发一个干净的 Ctrl+C。同时这段等待必须是可取消的——合成按键是一次性副作用，按键发出去之后就必须等它落地并还原，否则会漏在用户剪贴板上。

**四、UI 线程被 OLE 调用卡住**

Clipboard.GetDataObject() 是 OLE 调用，远端桌面、Office、第三方剪贴板管理器做延迟渲染时可以卡好几秒，在 UI 线程上就是整个窗口冻结。常见处理是丢到专用 STA 线程 + 信号量串行化 + 超时；重试只对 COMException / ExternalException 做，TimeoutException 一次都不重试（重试只会叠加卡死的线程）。

**五、UIPI**

管理员权限运行的窗口收不到普通进程的 SendInput（错误码 5，ERROR_ACCESS_DENIED）。这种情况要明确告诉用户，而不是静默失败。
```

### ③ 正文（可直接复制）

```
Windows 划词翻译，这次剪贴板真的不会被覆盖

用划词翻译读英文报错和文档，时间长了会发现，真正让人不安的不是翻译质量，是两件小事。

第一件：剪贴板。

划词翻译要拿你选中的文字，得模拟一次 Ctrl+C。问题是「拿完之后」——
翻译还没出结果的时候，你要是又复制了个文件路径，有些工具结束时会把剪贴板还原回去，你刚复制的就没了。

现在用的这个做法是看剪贴板的序列号：发 Ctrl+C 前记一个号，复制完了再记一个号。只有「最后一次写入确实是我这次复制」的时候才还原。中间你复制了新东西，序列号变了，它就不动。

读取剪贴板出错时也不会去清空——直接放弃这次划词。这个分支比你想的重要。

第二件：截图会不会被传上去。

截图翻译两条路：本机 OCR 出文字再翻译，或者整张图交给视觉模型。后者效果好，但图要离开本机。

这里的「图片外发」是一个单独的开关，默认关。关着就是本机 OCR。开了之后界面会写清楚图去了哪里：外网、局域网，还是根本没出本机。

另外有个「安全离线模式」，打开之后所有外发请求都不发，本机模型还能用。

第三件：译文和要点别互相覆盖。

点了「要点」译文就没了，这事踩过一次就忘不掉。所以工作台里要点是单独一栏，不会动译文。

说一下它现在不行的地方：

只支持 Windows 10/11。
需要自备 API Key。没配的话默认走 Google 公共翻译，就是能看懂的水平，技术文档别期待太高。
安装包没签名，第一次运行会有 SmartScreen 提示，点「更多信息 → 仍要运行」就行。介意可以下便携版解压即用，或者用发布页的 sha256 自己校验。
没有账号、没有同步、没有手机端。

快捷键记一下：
划词 Ctrl+Alt+W
截图 Ctrl+Alt+Space
查词 Ctrl+Alt+Q
工作台 Ctrl+Alt+O
关浮窗 Ctrl+Alt+X

开源，MIT，0.1.35。
```
