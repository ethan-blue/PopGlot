## 1. P0 清单（本批必做）

### OPT-001 · [性能] 主窗口隐藏到托盘后，2 秒轮询计时器永不停止

- **文件**：`apps/PopGlot.Windows/Sections/TranslateSection.xaml.cs:316`、`325-329`、`371`、`379`
- **关联**：`apps/PopGlot.Windows/MainWindow.xaml.cs:1082-1083`
- **问题**：`_sessionStorePollTimer`（2 秒）只在 `OnLoaded`/`OnUnloaded` 里启停。但 `MainWindow.OnClosing` 走的是 `e.Cancel = true; Hide();`（MainWindow.xaml.cs:1082-1083），而 WPF 中 `Hide()` **不会**触发 `Unloaded` 事件。结果：用户关窗到托盘后，这个计时器仍每 2 秒在 UI 线程唤醒一次并调用 `RefreshRestoreSessionAffordance()`，直到进程退出。
- **佐证**：全仓库只有 `QuickSearchWindow.xaml.cs:180`、`Sections/ServicesSection.xaml.cs:131`、`TranslationPanelWindow.xaml.cs:138` 挂了 `IsVisibleChanged`；**MainWindow 没有挂**，所以没有任何别的路径会去停这个表。
- **方案**：在 `TranslateSection` 构造函数里加
  ```csharp
  IsVisibleChanged += (_, _) =>
  {
      if (IsVisible) _sessionStorePollTimer.Start();
      else _sessionStorePollTimer.Stop();
  };
  ```
  并在 `OnLoaded` 里把无条件的 `_sessionStorePollTimer.Start()`（371 行）改为同样受 `IsVisible` 约束。不要动 `OnUnloaded` 的 `Stop()`（控件真正移除时仍要停）。
- **风险**：低。只影响计时器生命周期，不改任何业务逻辑。
- **验证**：开主窗口 → 关到托盘 → 任务管理器看 CPU 采样应回到 0（原本有周期性唤醒）。
- **改动量**：S

### OPT-002 · [性能] ~~设置读取每次都整文件读入 + SHA256~~ → **已撤销：不可做**

> **状态：2026-10-28 实施后撤销。** 原方案在正确性上不成立，工程师已回退，`ShellSettings.cs:688-708` 恢复为哈希校验（与基线逐字节一致），并新增 10 行注释锁死原因。**下批不要重新捡起这一条。**

#### 原方案（错误，存档用）

- 文件：`apps/PopGlot.Windows/ShellSettings.cs:661-720`
- 原判断：`LoadUnlocked()` 的缓存命中判断发生在读盘和哈希**之后**，每次调用都无条件 `FileInfo` → `ReadAllBytes` → `SHA256`，因此想把命中探针提到读盘前，改用 `(路径, LastWriteTimeUtc, Length)` 三元组判定。

#### 为什么不可做（已复核确认）

我在原方案里写的「(lastWrite, length) 二元组的碰撞概率对本地配置文件可忽略」是**错误的**——项目里本来就有 3 个测试**刻意构造**这个碰撞场景，属于锁死的正确性不变量，不是可忽略的边角。三个用例构造手法一致：改内容 → `File.SetLastWriteTimeUtc` 把时间戳钉回原值 → 显式断言字节长度不变：

| 用例 | 位置 |
| --- | --- |
| `ShellSettingsBomFileLoadsUserSettingsAndKeepsBytesCacheIdentity` | `tests/PopGlot.Windows.LogicTests/Program.cs:1734` |
| `ShellSettingsUtf16BomFileLoadsUserSettingsAndKeepsBytesCacheIdentity` | `tests/PopGlot.Windows.LogicTests/Program.cs:1798` |
| `QuickSearchHotkeyRegistrationSerializationAndDegradation` | `tests/PopGlot.Windows.LogicTests/Program.cs:4039` |

以 1798 为例：先载入含 `Ctrl+Shift+Y` 的 UTF-16 文件 → 记下 `cachedWrite` → 改写为 `Ctrl+Shift+Z` 并 `Equal(GetByteCount(orig), GetByteCount(rewritten))` 保证长度不变 → `SetLastWriteTimeUtc(path, cachedWrite)` 钉回时间戳 → 断言下一次 `Load` 必须返回 `Ctrl+Shift+Z`。**(路径, 时间戳, 长度) 三元组 100% 命中而内容已变**，我的探针会返回过期快照——用户改了设置却读到旧值。

**为什么没有折中空间**：不读盘就无法证明内容一致，`(lastWrite, length)` 不是可靠的内容变更信号。若把三元组降级为「快速失效」而非「快速命中」，匹配时仍要读盘 + 哈希确认，等于回到原点。

#### 收益判断同样错了

我原以为「缓存命中时读盘与哈希纯属浪费」。事实是：**读盘与哈希是命中判定的必要输入，不是浪费**。缓存真正省下的是 `DecodeJsonPayloadForDeserialization` + `JsonSerializer.Deserialize` + 整个 `new ShellSettings(...)` 构造。所以 28 个调用点的开销本来就低于我的描述，而「跳过反序列化」这个真实收益原实现已经拿到了。

#### 唯一可保留的安全部分（已并入 OPT-002R）

不动缓存判定，只**减少调用次数**是安全的。`MainWindow.OnClosing` 在同一个方法里调了两次 `ShellSettingsStore.Load()`：

- `MainWindow.xaml.cs:1075` → `.CloseMainWindowToTray`
- `MainWindow.xaml.cs:1094` → `.CloseHintShown`

两者之间只有 `Hide()` / `TrimWorkingSet()` / `NotifyTray`，**没有**写设置（写入在 1101 的 `ShellSettingsStore.Update` 之后）。可在方法顶部提升为一次 `var settings = ShellSettingsStore.Load();`，两处复用，省掉一次完整的读盘 + 哈希 + 路径。零行为变化。

**安全前提已由工程师二次复核确认**（他读了 `MainWindow.OnClosing` 1071-1111 全文，本人未实施）：

- 两次读取之间只有 `e.Cancel = true` / `Hide()` / `App.TrimWorkingSet()` / `_closeHintShown` 内存标志判断，**确实没有任何设置写入**
- 唯一写入是 1102 的 `ShellSettingsStore.Update(...)`，在两次读取之后

**下批实施时带上这两点**（工程师补充，避免踩坑）：

1. **提升不会新增读盘**：1075 本来就在 `if (!closeToTray) return;` 之前读了一次，非托盘路径也一样读到；合并后只是少读一次，不会把读盘挪到新的分支上。
2. **`_closeHintShown` 是内存短路标志，不能一并省掉**：它只保证 1094 的外层判断在同一进程内为真一次；内层 `shell.CloseHintShown` 承载跨进程/跨运行语义，仍要读文件。**只能共享同一次快照，不能把它优化掉。**

- **状态**：**下批首选项**（team-lead 裁决，本批不夹带——已进第 2 轮门禁收口，再动 C# 要重跑全量 verify.ps1，代价大于收益）
- **改动量**：S

### OPT-003 · [工程] 空闲内存指标口径错误，且 spec 数字与实测 artifacts 不一致

- **文件**：`PRODUCT_SPEC.md:195-198`；`artifacts/perf/startup.json:269-278`（真实数据）
- **问题**（两处，必须一起改）：
  1. **数字对不上**：`PRODUCT_SPEC.md:195` 写「空闲 WS=**103.53 MiB**」，而它自己引用的 `artifacts/perf/startup.json:270` 记录的是 `"workingSetBytes": 111403008` = **106.24 MiB**。
  2. **口径不可达成**：同一份 json 的 `"privateBytes": 63377408` = **60.44 MiB**。也就是说 WS 里约 **45.8 MiB 是共享代码页**（自包含 .NET 10 + WPF + WinForms 的映射映像页，多个 .NET 进程共享）。软目标 `wsTargetBytes = 83886080`（80 MiB）用 WS 口径衡量时，**即使把应用堆优化到零也到不了**。
- **方案**（改文档，不动代码）：
  1. PRODUCT_SPEC 验证段落的数字改为 **WS=106.24 MiB**，与 artifacts 一致。
  2. 并列记录 **Private Bytes = 60.44 MiB**。
  3. 加一句口径说明：「WS 含约 46 MiB 自包含运行时共享代码页，非本应用独占」。
  4. 把软目标重新表述为 **「Private Bytes 软目标 ≤ 80 MiB（当前 60.44 MiB，达成）」**，保留 **WS 硬门槛 ≤ 120 MiB（当前 106.24 MiB，达成）**。
  5. 原「80 MiB 空闲工作集软目标未达，作为开口保留」改为如实说明口径修正，不要再留一个架构上不可能达成的开口。
- **风险**：零（纯文档）。但收益很高——它让团队停止追一个假目标，也是 0.1.33 对外可如实陈述的一条实质进展。
- **注意**：**不要**为了让 WS 数字好看去做 `SetProcessWorkingSetSize` 之类的强 trim（`App.xaml.cs:2117` 已有 `TrimWorkingSet`，只在关窗隐藏时调用一次，这是对的；不要搬到空闲态常驻轮询）。
- **改动量**：S

- **问题**：三份方法体结构完全一致（乐观设置标签 → `SwitchActiveTemplateAsync` → 失败则 `RefreshStyleSelector()` → 成功且有原文则重译），差异只有三个参数：状态 TextBlock、原文 getter、重译入口。

  internal static async Task ChooseStyleAsync(
      PromptTemplateDto template,
      TextBlock label,
      Action<string> reportStatus,
      Func<string?> getText,
      Func<Task> retranslate)
  {
      label.Text = ShortLabel(template);
      if (!await SwitchActiveTemplateAsync(template.Id, reportStatus))
      {
          // 由调用方各自 RefreshStyleSelector
          return;
      }
      if (!string.IsNullOrWhiteSpace(getText()))
      {
          await retranslate();
      }
  }

- **风险**：中低。三个表面都已有各自的 `_isUnloaded`/`_isClosed`/`_closing` 守卫，抽取时要确认重译入口在各自守卫下仍被正确调用（查词版有额外的 `!_isClosed && IsVisible` 判断，必须保留在其 `retranslate` lambda 内，不能吞掉）。

### OPT-009 · [性能] HistoryStore 用 `File.ReadAllText` 同步读盘 → **建议下批**

- **文件**：`apps/PopGlot.Windows/HistoryStore.cs:270`（`LoadUnlocked` 内）；调用点 `apps/PopGlot.Windows/Sections/LibrarySection.xaml.cs:161`
- **问题**：`ReloadHistory()` 在 UI 线程上同步读整个历史文件（上限 4 MiB）。触发路径是 `MainWindow.RequestLibraryRefreshAfterFirstFrame()`（MainWindow.xaml.cs:976-985）里 `Dispatcher.BeginInvoke(..., DispatcherPriority.Background)`——虽然排在首帧之后，但**仍在 UI 线程上执行**，大历史库会造成一次可感知的卡顿。
  对比：`VocabularyStore.cs:705` 已经用了有界的 `ReadBounded(_storagePath, MaxFileBytes)`，HistoryStore 没跟上。
- **方案**（二选一，推荐前者）：
  1. 与 VocabularyStore 对齐：改用 `ReadBounded` + 严格 UTF-8 解码（复用其 BOM 剥离逻辑），顺带消除 `File.Exists` → `File.ReadAllText` 的 stat-then-read 竞态。

### 8.5 OPT-021 · [工程 · **新增**] LogicTests 结果不确定，质量门禁结论不可复现

> 这是本批审查**事后浮现但优先级最高**的一条。它不阻塞 0.1.33 的功能，但它直接动摇「门禁通过」这个结论本身的可信度，必须在 0.1.33 的「验证与边界」里如实披露，并作为 0.1.34 的 P0 处理。

#### 现象：同一命令、同一套测试，结果在两端之间跳

`dotnet run --project tests/PopGlot.Windows.LogicTests` 在本批内被两人各跑一次：

| 执行者 | 结果 | 合计 |
| --- | --- | --- |
| 工程师 | **361 passed / 0 failed** | 361 |
| 严过关 | **227 passed / 134 failed** | 361 |

**用例总数相同（361），通过与失败完全相反**，失败项全部是 `不能在同一 AppDomain 中创建多个 System.Windows.Application 实例`。这不是「哪个入口受支持」的问题，是**结果不可复现**。

#### 历史数据：波动幅度远不止这一次

| 来源 | 结果 |
| --- | --- |
| `artifacts/ci-0.1.31-complete.log`（CI Release） | 347 passed / **0 failed** |
| `artifacts/c09-final-run.log` | 257 passed / 0 failed |
| `artifacts/logic_tests_release_full.log` | 207 passed / 0 failed |
| `artifacts/logic-0.1.31-release.log` | 345 passed / 2 failed |
| `artifacts/agentB-logic-tests.log` | 222 passed / 10 failed |
| CHANGELOG 0.1.32 | 360 passed / 1 failed |
| `logic_test_run.log`（2026-09-26） | 203 passed / **84 failed** |

CI（Release）是干净的 347/0，多次本机运行也干净，但出现过 84、134 两次大规模失败。**注**：`logic_test_run.log` 是 2026-09-26 的产物，早于 0.1.32 的修复，所以不能用它论证「该问题长期存在」——但 AppDomain 报错模式是真实的，且在本批内再次出现。

#### 必须纠正一个会误导的判断

工程师的结论是「单独 `dotnet run` 是不受支持的入口，唯一受支持的入口是 `scripts/verify.ps1`」。**这个二分不成立**：

```powershell
# scripts/verify.ps1:35 —— 与「不受支持的独立入口」是同一条命令
& $dotnet run --project (Join-Path $PSScriptRoot '..\tests\PopGlot.Windows.LogicTests\...csproj') --configuration Debug
```

verify.ps1 相对裸命令**只多了**两件事：前面先 `dotnet build` app 项目、先跑 PureTests。两者都不改变 LogicTests 进程内的 AppDomain 行为。

所以：**如果裸命令是非确定的，`verify.ps1` 同样暴露在这份非确定性之下**——它只是之前每次都运气好。把它标记为「不受支持的入口」会制造一种虚假的安全感，这比问题本身更危险。正确表述是：**LogicTests 套件本身结果不确定，与调用方式无关。**

#### 根因假设（待 QA 实证，我不下定论）

1. **失效点是 `EnsureApplication()`**（`tests/PopGlot.Windows.LogicTests/Program.cs:9964`）：守卫条件为 `if (Application.Current is null)` 再 `new App()`。`Application.Current` 是**按线程**解析的，一旦某个测试在非 UI 线程上触发 `EnsureApplication`，`Application.Current` 在那里为 null 而 AppDomain 已有实例 → 抛出该异常。
2. **级联放大**：异常发生在套件前段时，后续所有触碰 WPF 的用例会连锁失败。这解释了为什么失败数总是成片出现（84、134）而不是零散几个。
3. **可能的外部触发**：`TestIsolation.AssertNoConflictingAppInstance`（`TestIsolation.cs:138-145`）是套件第 2 个用例，明确断言「没有真实 PopGlot 实例在运行，请从托盘退出后重跑」。说明套件的正确性依赖宿主机状态（真实 PopGlot 进程 / 并发的测试宿主进程）。开发机上 PopGlot 常驻托盘，CI 上没有——**这与「CI 干净、本机波动」的观测一致**，是最值得先验证的一条。

#### 建议处置

- **0.1.33（本批）**：不做代码改动。但在 CHANGELOG「验证与边界」里如实写明「LogicTests 存在已知的入口无关型结果波动，本批数字以第 N 轮 verify.ps1 输出为准」，不要写一个无法复现的数字。
- **0.1.34（P0）**：
  1. 先验证假设 3：在「有真实 PopGlot 运行」与「无」两种状态下各跑一次，确认是否可复现。
  2. 若成立，二选一：(a) 把 `AssertNoConflictingAppInstance` 从「用例」提升为 `Main` 入口的**前置硬门禁**（冲突即中止，而不是变成一次 FAIL 后继续跑出 134 个级联失败）；(b) 让套件对该状态免疫。
  3. 让 `EnsureApplication()` 的失败**快速失败**而非级联——一个守护点坏了不该污染其余 300+ 用例。
- **改动量**：M（需先做 1 的定位实验）

#### 对清单其他条目影响

- OPT-016（verify.ps1 全 Debug vs release.yml 全 Release）优先级**上调**：两份门禁配置不同 + 套件结果不确定，两者叠加意味着「本机通过」几乎不携带信息。
